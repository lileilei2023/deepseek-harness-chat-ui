# DS Chat 设计评审与优化方案

> 评审对象：`source/client-ui-skill-chat`（React UI + CSS Modules）与 `source/workbuddy-skill-catalog`（宿主服务）
> 评审版本：`0.1.0-alpha.1`（DeepSeek Harness `0.1.2-alpha.5`）
> 评审日期：2026-09-05

## 一句话结论

DS Chat 的产品概念（把 Skill 拟人化成可对话的联系人与群组）是成立且有区分度的，但**实现层面绕开了宿主的设计令牌体系**：171 处硬编码色值、2 个从未定义的令牌、0 处暗色适配，导致它在暗色模式下基本不可用，视觉语言也停留在渐变高光的拟物风格，与 Harness 外壳和 Apple 现行设计语言都不一致。

---

## 一、做得好的地方

先说不该动的部分，这些是产品价值所在：

1. **拟人化身份是真差异点**：确定性昵称 + 圆形动物头像 + 档案页，让 Skill 从"下拉菜单里的一行字"变成可辨识的协作对象。这比 ChatGPT 式单助手外壳更贴近真实协作心智。
2. **Room 持久化**：重开会话恢复上下文而不是静默新建，这是对话产品的正确默认值。
3. **不选 Skill 也能聊**：`开始普通对话` 保留了零门槛入口，没有强迫用户先做选择题。
4. **群组的 System Prompt 是可复用资产**：群职能 + 协调者的建模比"临时多选几个 Agent"更有沉淀价值。
5. **皮肤系统有契约意识**：`DSH Web Skin Manifest v2` 把主题做成声明式包，而不是散落的样式覆盖。

## 二、三个致命问题

### 致命问题 1：暗色模式下产品不可用

**证据（可复现）**：全部三份样式表中，`prefers-color-scheme`、`data-theme`、`data-ds-dark-theme` 的出现次数为 **0**。而 Harness 自身有完整明暗体系（`body[data-ds-dark-theme]` 切换 78 个 `--dsw-alias-*` 令牌），用户设置里 `ui-theme.preference` 可选 dark。

Harness 自己的开发规范原文写着：

> Use the theme CSS variables (`var(--dsw-alias-bg-layer-1)`, `var(--dsw-alias-label-primary)`, …) instead of literal colors, **or your contribution breaks in the other color scheme**.

插件违反了这条规范 **171 次**（硬编码 hex），其中 19 处 `#fff`、多处 `color-mix(..., white)`、多处 `rgb(255 255 255 / x%)` 内高光，全部假设背景是白色。

**实测后果**：在暗色外壳下，会话区渲染为白底白字——助手回复完全不可见；`开始普通对话` 卡片标题消失；侧栏面板变成深色外壳上突兀的白色板块。

**为什么是致命的**：这不是"不好看"，是功能性失效。用户切到暗色主题后读不到模型的回复。

### 致命问题 2：两个令牌从未定义，导致悬停与凹陷层永不渲染

**证据**：交叉比对插件引用的令牌与 Harness 主题定义的令牌：

| 令牌 | 插件引用次数 | 宿主是否定义 |
| --- | --- | --- |
| `--dsw-alias-bg-subtle` | 38 | **否** |
| `--dsw-alias-bg-hover` | 12 | **否** |

宿主的正确名字是 `--dsw-alias-bg-layer-1/2/3` 与 `--dsw-alias-interactive-bg-hover`。

按 CSS 规范，`var()` 引用未定义自定义属性且无 fallback 时，该声明在 computed-value 阶段失效；更严重的是这两个令牌大量出现在 `linear-gradient(...)` 与 `color-mix(...)` 内部，**整个函数值一并失效**，声明被丢弃。

**实测后果**：全部悬停反馈、搜索框底色、Tab 轨道、凹陷面板背景**从未绘制过**。界面看上去"发飘、层级不清"，根因在此，而不是设计取向。

### 致命问题 3：排版没有尺度，正文与辅助信息不可区分

**证据**：

- 字号使用 **16 个不同值**，分布为 11px×36、12px×30、10px×24、13px×23、9px×5……最高频的三档是 10–12px。
- 字重使用 **11 个不同值**：650、600、400、700、750、760、720、680、620、580、500。

**后果**：正文与次要说明只差 1px、字重只差 30，视觉上几乎同级，用户必须逐字读完才能建立层级。同时 9px/10px 低于长时间阅读的舒适下限。11 个字重里多数（650/680/720/750/760）在真实字体中并不存在对应字面，浏览器合成后笔画粗细不可控。

## 三、动线问题（用户路径）

侧栏自上而下：**项目空间 → Tab → 显示模式 → 外观与皮肤 → 内容**。四层常驻控件之后才是内容。

实测（1400×900 视口，侧栏高 724px）：内容首行位于距顶 **214px**，即 **29.5% 的垂直空间被控件占用**。

具体问题：

1. **「显示模式（拟人／原始）」常驻一整行**：它只影响联系人/Skill 的显示名，对「消息」「自动化」两个视图毫无作用，却在所有视图里占位。低频全局开关占据高频位置。
2. **「外观与皮肤」被钉在会话列表之上**：皮肤是偏好设置，不是导航。侧栏底部已有「设置」入口，这里属于职责错位。
3. **「会话历史」排在最底部**：对回访用户，"继续上次那段对话"是最高频意图，却被放在群组列表之后。
4. **群组为空时占用整块空状态卡**：把本就靠后的会话历史继续下推。

## 四、视觉语言：不是 Apple 风格，是 2010 年代拟物

现行实现的材质构成：

```css
background: linear-gradient(180deg, var(--bg-base), var(--bg-subtle));   /* 竖向渐变 */
box-shadow: 0 12px 34px rgb(24 35 46 / 12%), inset 0 1px 0 rgb(255 255 255 / 72%);  /* 内白高光 */
border: 2px solid rgb(255 255 255 / 88%);                                 /* 白色描边"贴纸" */
transform: translateY(-1px);                                              /* 悬停上浮 */
```

这四件套（竖向渐变填充 + 内侧白色高光 + 白圈描边 + 悬停位移）正是 Apple 在 iOS 7 / macOS Yosemite 之后**明确放弃**的语言。现行 Apple 设计语言的对应做法是：

| 维度 | 现状 | Apple 现行做法 |
| --- | --- | --- |
| 填充 | 竖向渐变 | 平整填充；层级靠半透明灰阶 fill |
| 描边 | 1–2px 实色/白色 | 0.5px 发丝线（Harness 已于 2026-09-01 迁移，插件未跟进） |
| 高光 | `inset 0 1px 0 #fff` | 无 |
| 阴影 | `0 12px 34px` 重投影 | 仅浮层使用，且低对比 |
| 悬停 | `translateY(-1px)` 位移 | 改变填充；控件不移动 |
| 圆角 | 10/11/12/16/17/18/22 混用 | 固定尺度 |

`translateY(-1px)` 还有可用性代价：悬停时控件从指针下方移开，快速连点容易落空。

## 五、优化方案（已实施）

### 5.1 建立令牌层 `theme.css`

新增单一令牌来源，分两层声明：

- `:root` —— 排版尺度、4pt 间距、圆角、强调色渐变、阴影、动效、代码面板配色。
- `body` —— 所有派生自宿主 `--dsw-alias-*` 的令牌。

**为什么必须分两层**：Harness 把调色板发布在 `body` 上。若在 `:root`（即 `<html>`）声明 `--ds-chat-surface: var(--dsw-alias-bg-base)`，该 `var()` 在 html 元素上找不到别名，整个令牌变成 guaranteed-invalid 并以空值向下继承——这正是致命问题 2 的同类错误。此处已实测验证（改前 `--ds-chat-hover` 计算值为空串，改后为 `#2631480f`）。

暗色仅靠 `body[data-ds-dark-theme]` 覆盖令牌实现，不重复任何布局规则。

### 5.2 消除字面色值

| 指标 | 改前 | 改后 |
| --- | --- | --- |
| 组件样式表中的硬编码色值 | 171 | **3**（头像默认三色，本就按头像覆盖） |
| 未定义令牌引用 | 50 | **0** |
| `translateY` 位移动效 | 8 | **0** |
| 浅色专用构造（白描边／白高光／`, white)` 混色） | 29 | **0** |

约 50 个近似绿色（`#16834a`/`#20b967`/`#2fcf72`/`#38ad70`/`#22c76e`…）归并为单一强调色渐变，其余色阶由 `color-mix()` 从 `--ds-chat-accent-solid` 派生。

### 5.3 排版收敛到尺度

7 档字号（11/12/13/14/15/17/20）各有明确角色；字重收敛为 400/500/600/700 四档；9px、10px 一律提升至 11px。行标题与副行拉开一档字号 + 一档字重 + 一档颜色，三重区分。

### 5.4 视觉语言换为平整材质

平整填充 + 0.5px 发丝描边（对齐宿主 2026-09-01 规范）；阴影收敛为三档且仅用于浮层；悬停改变填充而非位移；按下用 opacity 变暗；圆角统一为 6/8/10/12/16/20 尺度；用户气泡改为强调色实底（Apple Messages 语汇）。

### 5.5 动线重排

- 「显示模式」从常驻栏移入**联系人视图**（它唯一生效的地方），并改为分段控件样式。
- 「外观与皮肤」下移至底部设置区。
- 「消息」视图顺序改为：快捷入口 → **最近对话** → 群组。
- 群组空状态由整块卡片改为一行说明。

**实测效果**：内容首行距顶 214px → **127px**，常驻控件占比 29.5% → **17.5%**，会话列表进入首屏。

### 5.6 皮肤契约简化

内置皮肤原先各自重述 15 条令牌（含未定义令牌与白色渐变）。改为只声明**身份（强调色）与形状（圆角）**，其余由令牌层派生，并各自附带暗色变体。皮肤不再能钉死 surface —— 这正是暗色失效的成因之一。

## 六、可用性扩展：多来源 Skill 导入（已实施）

**原限制**：目录服务只扫描单一根目录 `~/.workbuddy/plugins/cache/workbuddy-builtin`，且 `readContact` 强制要求 `<plugin>/<version>/` 两级路径。

**实测本机可发现的 Skill 数量**：

| 来源 | 路径 | 布局 | SKILL.md 数 | 改前是否导入 |
| --- | --- | --- | --- | --- |
| WorkBuddy | `~/.workbuddy/plugins/cache/workbuddy-builtin` | `<plugin>/<version>/` | 46 | 是 |
| Claude Code | `~/.claude/skills` | 扁平 + 一层 bundle | 291 | **否** |
| Claude 插件市场 | `~/.claude/plugins/marketplaces` | 嵌套 | 33 | **否** |

**改动**：`Config` 新增 `roots` 列表（`{ id, label, path, layout }`），默认包含上述三个来源；`readContact` 改为布局容错——`version` 变为可选，仅当第二段路径形如版本号时才识别为版本，否则视为 bundle 内的嵌套 Skill；同名 Skill 按 roots 顺序取先者。联系人徽章显示真实来源标签而非一律 "WorkBuddy"。

`config.root` 保留向后兼容：设置时仅改写默认 roots 中 workbuddy 一项的路径。

### 连带修复：一个坏文件会让整份联系人列表加载失败

接上多来源后立刻暴露了一个既有缺陷：`parseFrontmatter` 直接调用 `parseYaml`，未做保护。`~/.claude/skills` 中有 SKILL.md 的 description 含未转义冒号（`install first: npm i -g thing`），YAML 解析抛出后沿调用栈上抛，**整次扫描中止**，界面显示「联系人加载失败」，所有来源的联系人一个都不显示。

原代码只扫 WorkBuddy 一个来源（46 个文件、frontmatter 规整），因此从未触发。改为解析失败时跳过该文件，并补了回归测试。

### 连带修复：名字池撑不住真实规模

拟人昵称池只有 **24 个**名字，冲突时追加 base36 哈希后缀。48 个联系人时基本不冲突；接入三个来源后变成 334 个，约九成联系人显示成 `松松·1B`、`悠悠·PR` 这类机器码——而拟人化正是这个产品的核心差异点。

名字池扩到 **96 个**，冲突后缀改为可读序号（`松松2`）。实测 334 个联系人中带哈希后缀的数量为 **0**。

**实测结果**：联系人 48 → **334**（Harness 2、Claude 259、WorkBuddy 46、Claude 插件 27），扫描耗时 119ms。

## 十、第二轮：侧栏结构性重做与弹窗修复

第一轮解决的是**材质与令牌**（暗色、色值、排版尺度）。这一轮解决的是**结构与动线**，起因是用户对照 Teamily 指出图标、动线、排版仍有差距，并具体点名了侧栏的加号数量与新建群聊弹窗。

### 10.1 先说清能借与不能借

插件只挂宿主两个槽：`sidebar.workspaces`、`sidebar.brand.name`（`index.ts:145`、`:241`）。侧栏宽度 280px 由宿主 `.sidebarCol` 决定，插件得到 268px；`新会话` 按钮与 `设置` 分属宿主的 `dsh-client-ui-sidebar` 和 `dsh-client-ui-settings-general`。

**因此 Teamily 那条独立图标导航栏（聊天/智能体/自动化/发现/记忆/我）不在插件可控范围内，本轮不做。** 可借的是它的其余特征：单一列表、单一新增入口、常驻搜索、统一行结构、次要元数据降级为灰字。

### 10.2 为什么是「合并」而不是「换位置」

用户问要不要把最近对话与群组换位置。数据模型给出了更根本的答案：

`ChatRoom` 持有 `sessionIds: readonly string[]`（`model.ts:51`），`RoomSession` 是房间内的实例（`model.ts:30`）。于是**一个群组在「群组」段出现 1 次，它的 N 个会话在「最近对话」段又出现 N 次**——同一对象、两种粒度、两个位置。这才是冗余感的来源，调换顺序不解决。

改为：列表对象是 **Room，按 `updatedAt` 倒序**，行结构统一为 `头像 | 标题 + 副行 | 时间`。群组身份由头像堆叠 + 副行成员数表达。会话级历史保留在房间头部已有的「历史」菜单（`openHistorySession` 仍被 `:1031` 引用），职责归位。

行文案也去重：新会话的标题等于房间标题，原实现会把同一字符串在标题、meta、副行打印三遍。

### 10.3 新增入口 4 → 1

审计出插件内 4 个新增入口，其中 **tab 栏的 `＋` 与群组段的 `＋ 新建` 是同一个 handler**（`openGroupCreator`），纯重复。另外宿主的 `新会话` 按钮和 logo 都会触发 `startSession()`，是插件之外的第 5、6 个入口。

改为一个 `＋` 菜单（普通对话 / 群聊 / 项目目录）。「添加工作区」并入项目空间下拉菜单末项。

| 指标 | 改前 | 改后 |
| --- | ---: | ---: |
| 插件内新增入口 | 4 | **1** |
| 常驻控件高度 | 214px | **131px**（且新增了常驻搜索） |
| 消息视图分段数 | 3 | **1** |

### 10.4 新建群聊弹窗：三处结构性缺陷

**缺陷 1 —— 两列不等高（用户已指出）**。`.groupFormGrid` 是 `minmax(0,1fr) minmax(0,1.45fr)` 双列，名称 `<input>` 与职能 `<textarea>` 落在同一 grid 行；行高由 `textarea` 的 `min-height: 110px` 决定，而 `.field` 默认被 `stretch` 拉伸，导致短字段的 label 与 input 之间浮出空白。改为单列两行，问题从根上消失。

**缺陷 2 —— 成员列表「不能拖动」的真实原因**。`.groupCandidates` 其实设了 `overflow-y: auto; min-height: 0`，但**没有 `flex` 值**，在 `flex-direction: column` 容器里是 `0 1 auto`——它不争取空间。兄弟节点全部默认 `min-height: auto` 拒绝收缩，算下来只剩约 115px，而一行成员 64px，**所以只能显示 1–2 行**。不是不能滚，是视口被挤没了。

**缺陷 3 —— footer 会被裁掉**。`.groupDialog` 是 `overflow: hidden` 且无外层滚动。`.workspaceBindings` 无 `max-height`，绑定目录越多固定区越高；一旦超过 720px 上限，`创建` 按钮直接被裁出可视区——**功能不可达**。

改为三段式：头部固定 / 中部两个各有保底高度的滚动区 / 底部固定。并按主次重排——`创建` 在选够 2 人前是禁用的，说明选成员才是主任务，于是头像库、群组职能、绑定目录收进「更多设置」折叠区。

实测（1400×900）：footer 始终可见；成员区 293px、可滚、承载 334 项；展开折叠区后成员区仅从 293px 变为 290px。

### 10.5 指南审计修复（vercel Web Interface Guidelines）

| 项 | 处理 |
| --- | --- |
| 大列表未虚拟化（334 项） | `.roomList`/`.list`/`.groupCandidates` 用 `content-visibility: auto` + `contain-intrinsic-size`（指南列出的方案之一，零依赖）。占位高按实测校准：房间行 56px、联系人行 58px——占位值与真实值不符会让滚动条失真。 |
| 破坏性操作无确认 | `归档群组` 增加二次确认对话框，文案说明历史会话保留且无撤销入口。 |
| 表单可访问性 | 4 个输入框补 `aria-label`，补 `autoComplete="off"`、`spellCheck={false}`、`type="search"`；8 处 placeholder 补 `…` 结尾。浏览器实测 7 个输入框可访问名覆盖率 100%。 |
| 暗色原生控件 | `theme.css` 声明 `color-scheme: light` / `dark`（实测 body 计算值为 `dark`）。 |
| 触摸与数字对齐 | `.root` 补 `touch-action: manipulation`；时间、计数补 `font-variant-numeric: tabular-nums`。 |

## 十一、第三轮：头像身份、列对齐与对话区从属化

用户要求把产品当作「agent 的交友/聊天软件」来做，风格要明显；并具体指出头像丑、图一不等长、右侧割裂。

### 11.1 头像：24 张图 → 分层生成

原实现只有**一张脸**：固定圆形脸盘 + 两个点眼 + 一条嘴，靠三种耳朵形状（尖/大圆/长）和 **6 个配色**区分，合计 24 张图要分给 334 个联系人。拟人化是这个产品的立身之本，头像却是它最薄的一环。

改为四层生成，全部由种子推导，无外部资源：

| 层 | 数量 | 说明 |
| --- | ---: | --- |
| 物种轮廓 | 24 | 耳形 + 脸型几何 + 专属斑纹（熊猫眼圈、浣熊面罩、虎纹、猪鼻、鹿角、蝠耳、蛙顶眼、企鹅腹、羊毛、六角恐龙外鳃…） |
| 配色 | 16 | 底色 / 主色 / 墨色三元组 |
| 表情 | 6 眼 × 5 嘴 | 由 Skill 自身 id 推导 |
| 配饰 | 8（含无） | 眼镜、耳机、围巾、帽子、花、领结、天线 |

可选身份 24 × 16 = **384** 个供用户挑选；表情与配饰再由 Skill id 派生，因此同species 同配色的两个 Skill 仍是两个角色。

**关键修正**：仅扩库不够。`ensurePersonas` 只给新联系人分配头像，已有 persona 保留旧 `avatarId`，实测扩库后仍然只渲染出旧库的 12 个物种。改为：**用户自定义过的头像保持不动，从未自定义过的跟随当前库**。实测 24 个物种全部出现，分布 7–23 均匀。

**两次迭代**：第一版脸盘 r=18 过大盖住耳朵、耳朵与脸同色，放大后仍是"带耳朵的圆球"。第二版给每个物种独立脸型几何（rx/ry/cy），耳朵加深一档（`color-mix(main 78%, ink)`），轮廓才真正可辨。

### 11.2 列对齐：5 个左边界 → 1 个

实测这一列有 **5 个不同左边界、5 个不同右边界**：

| 元素 | 左 | 右 | 归属 |
| --- | ---: | ---: | --- |
| DS Chat 品牌 | 16 | 232 | 宿主 |
| 新会话 | 14 | 266 | 宿主 |
| 项目空间 | 20 | 230 | 插件 |
| Tab / 搜索 | 12 | 280 | 插件 |
| 设置 | 10 | 270 | 宿主 |

插件的宿主槽 `regionArea` 本身相对侧栏左偏 8px、右侧齐边，因此用一处补偿性 `padding`（左 2 / 右 14）把插件全部行对齐到 **14 → 266**，即与最显眼的邻居「新会话」完全一致。项目空间选择器原先还为已移除的 ＋ 保留着一列 34px 网格，一并去掉。

### 11.3 对话区：轨迹从平级降为从属

宿主把每个流节点按同一层级、同一权重排布，于是「1 条提问 + 22 条思考 + 22 条 Bash」渲染成**一个气泡压着 44 行终端日志**——左边是聊天软件、右边是控制台，这道缝就是割裂感。

改为：轨迹缩进到头像列之下，共用一条导轨与浅色底，字号降一档、默认 62% 不透明度，hover/focus 恢复；连续轨迹之间取消间距，使一段轨迹读作**一块工作笔记**而非 44 条平级消息。

**实现方式的取舍**：钩子用宿主的语义属性 `data-chat-flow-kind`（`user` / `assistant-step` / `tool-call` / `system-prompt` / `turn-process`），而非 hash 化的 CSS module 类名（`EvIC1a_flowItem` 这类每次构建都会变）。这仍然耦合宿主版本，但失效时只是规则不匹配、回落到宿主原样式，不会破坏渲染。

### 11.4 死代码清理

跨全部源文件比对后，删除**整条选择器全部无引用**的规则块 130 条，样式表 84.9KB → 64.8KB（−24%）。删除后重新构建、24 项测试通过、界面渲染正常。

- **宿主自身的 3 个不同边界**（品牌 16、设置 10、收起按钮 240）：属于另外两个宿主包，插件可用全局 CSS 强行对齐，但那是伸手改别人的 DOM，收益不抵脆弱性。
